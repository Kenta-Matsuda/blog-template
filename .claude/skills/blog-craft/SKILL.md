# 価値のあるブログ記事を書く

`LESSONS.md` の個々の指摘を、題材によらず使える形にまとめたもの。末尾の括弧は教訓の ID を示す。`ST-` で始まる ID は、[slide-template](https://github.com/Kenta-Matsuda/slide-template) の `LESSONS.md` の教訓を示す。

## 0. 5 つの原則

すべてのルールは、次の 5 つのどれかから来ている。迷ったらここに戻る。

1. **読者を 1 人に決める**：読者が決まると、書く話と削る話が決まる。（L002）
2. **著者にしか書けないことを書く**：読者が AI に聞いても得られない情報が、記事の価値になる。数字、失敗、理由、気づきが該当する。（L001）
3. **事実で言い、強さを事実に合わせる**：エージェントの記憶で事実を書かない。確かめていないことは書かないか、確かめるよう著者に伝える。（L007, ST-L003）
4. **初めて読む人に通じるようにする**：前提、主語、用語、話のつながりを省かない。（ST-L019, ST-L037）
5. **著者の判断を正とする**：著者が直した文と言葉を、指示なく変えない。公開版を次の記事の教材にする。（L021, ST-L030）

## 1. 進め方

| 段階 | やること | 確かめること |
|---|---|---|
| 読者 | 読者を 1 文で書き、著者に確かめる | その読者が記事を読んだ後に何をするかを言えるか（L002） |
| 材料 | 著者に具体的な材料を聞く。聞いた材料が無ければ、本文を水増ししない | 2 章の質問に答えがあるか（L001） |
| 構成 | 見出しの一覧を出す。著者が迷っている内容は、先に壁打ちする | 見出しだけを順に読んで話が通るか（ST-L012） |
| 下書き | 著者の言葉を使って書く。分からない箇所は聞く | 著者の気持ちや動機を創作していないか（L005） |
| 日本語 | `natural-japanese` の順序で直す | 同スキルの確認リスト |
| 点検 | `npm run check -- 記事.md` を実行し、初見の読者役のサブエージェントに通読させる | 初出の用語、突然出る話、前後の矛盾（ST-L037） |
| 手直し | 著者が直して投稿する | 投稿は著者が判断する |
| 振り返り | `/retro` で、下書きと公開版の差分から教訓を残す | 差分の理由を推測したものは、推測と書く（L021） |

## 2. 著者に聞くこと

記事の価値は、次の答えで決まる。エージェントが埋められないので、著者に聞く。

- 読者は誰か。その人は読む前に何に困っているか。
- 普段と比べて何がどのくらい違ったか。数字で言えるか。（例：普段は 30 分以上余るが、今回は 1 分だった）
- 何に失敗したか。なぜ失敗したか。（例：違うアカウントで申し込んだので、延長の申請を忘れた）
- 具体的に何をしたか。なぜ効果があったか。（例：末尾の一文を先に読むと、キーワードを見つけやすい）
- 読者がすぐに使える情報は何か。
- 他の記事に書いていない気づきは何か。（例：簡単な単語の組み合わせほど、意味を間違えやすい）
- 省いてよい話は何か。（例：自作サイトの改善の余談）

## 3. 構成

- **冒頭に、誰に向けた記事で、何が分かるかを書く。** 枠に入れるなら、ここに 1 つ使う。
- **読者の疑問の順に並べる。** 実際の記事は「はじめに → どんな試験か → 何を勉強したか → 当日どうだったか → 何をすべきか → 受けてよかったこと → おわりに → 付録」の順である。
- **体験談と読者への助言を分ける。** 体験を書いた後で、読者がすべきことを節として独立させる。（L017）
- **全体から個別の順に書く。** 細部に入る前に、全体を示す。（ST-L021）
- **前提になる用語は、使う前に説明する。** 略語は初出で正式名と意味を書く。（ST-L019, ST-L022）
- **新しい話題は、前の内容から生まれる問題として導入する。**（ST-L037）
- **並べる項目は、同じ種類、同じ形にそろえる。** 「①シンプルに難しい単語」と「②簡単な単語の組み合わせ」のように同じ軸で分ける。（ST-L008）
- **本文の数と項目の数を合わせる。** 項目を増減するなら「次の3つ」のような数を直すか、「以下の通り」に変える。（L022, ST-L034）
- **付録に本文の繰り返しを置かない。** 本文で省いた詳細を置き、なぜ役に立つかを本文で一言添える。（ST-L018）
- **筋に関係の薄い話は削る。** 著者が入れたい話でも、読者に関係するかを著者と相談する。（L019, ST-L031）
- **おわりには、読者の次の行動を書く。** 感想ではなく、読者がすることを短く並べる。（L017）

## 4. 例と表の作り方

- **一覧が全部ではないときは、例だと分かるように書く。** 列名を「例」にする方法がある。（L009）
- **読者がどう誤解するかを見せる。** 著者は「直訳」の列を足して「デザインによる責任？」「優雅な失敗？」と書いた。意味だけを書くより、なぜ間違えるのかが伝わる。（L009）
- **例は、著者が実際に大事だと思うものに絞る。** 用語の全量は付録に回す。（L001）
- **比較には、読者が知っている基準を使う。** 「長い」ではなく「CLFほど短くはないが、SAPほど長くもない」と書く。（L008）
- **AI が作った一覧は、そのまま価値にならない。** 著者が選ぶ、一言を足す、分類するなどの手を入れる。（L001）

## 5. 事実と根拠

- 数字、仕様、制度は、著者の情報か公式ドキュメントで確かめる。（L007, ST-L003）
- 読者が手順どおりに行動する情報は、公式ページへのリンクを貼るか、確かめていない手順を書かない。（L007）
- 他の人の主張は「〜によると」、自分の考えは「〜と思います」と書き分ける。（ST-L003）
- 分からないことだけを伝える文は書かない。（ST-L042）
- 規模の主張は、数えられる指標で示す。（ST-L052）
- 著者自身の話を、読者全員に当てはまる話として書かない。（L006）

## 6. Qiita の記法

| 記法 | 使いどころ | 注意 |
|---|---|---|
| `:::note info` | 冒頭の対象読者と要約 | 枠は記事全体で数個までにする（L018） |
| `:::note warn` | 読者が誤解しやすい前提 | 例：「この勉強期間は誰にでも当てはまらない」 |
| `:::note alert` | 読者の不利益につながる注意 | 乱用すると効果が無くなる |
| `<details><summary>題</summary>` | 長い用語集のような付録 | `<summary>` の後に空行を入れると、中の表が表示される |
| `[^id]` | 本文の流れを止めたくない補足 | 定義は `[^id]: 説明` の形で書く |
| URL だけの行 | 関連記事のリンクカード | 前後に空行を入れる |
| 絵文字 | 原則使わない | 著者が「消して」と指示した（L018） |
| `https://qiita.com/ユーザー/items/ID.md` | 公開版の Markdown の取得 | 振り返りの差分に使う |

## 7. 投稿前の点検

- [ ] 投稿用メモ、TODO、HTML コメントを消したか
- [ ] タイトルは内容をそのまま表しているか（L020）
- [ ] 冒頭に読者と内容を書いたか
- [ ] 本文の数と項目の数が合っているか
- [ ] 事実と手順を、公式の情報か著者の情報で確かめたか
- [ ] 枠、太字、絵文字を絞ったか
- [ ] 初見の読者役のサブエージェントに読ませ、指摘の裏を取ったか
- [ ] `natural-japanese` の確認リストを終えたか
- [ ] Qiita のプレビューで、枠、表、折りたたみ、脚注の表示を確かめたか
- [ ] 投稿は著者が判断したか

## 8. このスキルを育てる

- 新しい指摘は `/lesson` で `LESSONS.md` に足す。
- 投稿後は `/retro` で公開版との差分を読み、教訓を整理する。
- 日本語の直し方は `natural-japanese` に、実際の前後の例を添えて足す。
